# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A TypeScript MCP server for INAVI Maps. MCP hosts spawn it as a subprocess and talk to it over
**stdio** — there is no HTTP server. It gives AI assistants three groups of reference tools:
map HTML examples, INAVI Maps API specs, and Web JS SDK docs.

`src/server.ts` is the entry point; tools live in `src/tools/`, env config (Zod-validated, fails
fast) in `src/config/env.config.ts`.

## Release

Releases run from GitHub Actions, not the shell (`npm run release` only prints a pointer and
exits 1):

```
Actions > Release > Run workflow > version-type: patch | minor | major | none
```

The workflow bumps the version (`scripts/sync-version.js` syncs `manifest.json` and
`server.json` through the npm `version` hook), pushes the commit and tag to `main`, publishes to
npm, waits until npm serves the new version, publishes to the official MCP Registry, then
creates a GitHub Release. MCPB (`.mcpb`) bundles are no longer built; `manifest.json` stays and
is still kept in sync.

**Do not bump the version locally** — the workflow does it, so a local `npm version` makes the
release skip a number.

`none` publishes the version already on `main` without bumping. It is the resume path for a run
that failed after the version reached `main`. Run it once — a second run fails when the MCP
Registry rejects the duplicate version.

### Release notes

A `patch` release keeps the generated `## What's Changed` list on its own.

A `minor` or `major` release gets a `## Highlights` section that the workflow leaves reading
`_Pending._`; fill it in afterwards from the diff between the two tags. One line per item:

- new tools or capabilities — what the user can now do that they could not before
- changed behaviour or meaning — the most important category; a field that now means something
  else belongs here even when nothing breaks
- visibly different output

Leave out refactors, CI work and dependency bumps.

## Environment Variables

All optional:

- `NODE_ENV` — `development` (default) | `production` | `test`
- `PORT` — default `3000`
- `INAVI_DOMAIN` — default `https://imaps.inavi.com`; `/maps/v3.0` is appended automatically

Server name and version come from `package.json`.

## SDK Docs Pipeline

`npm run update-sdk-docs` reads the Docma SPA's parsed JSDoc data at `window.docma.apis`
(structured data, not HTML) and writes per-symbol JSON to `public/sdk-docs/`. Validate the
result with `npm run validate-sdk-docs`.

- Categories are **derived** from structure/naming — no hardcoded symbol lists — so the pipeline
  stays correct when the source SDK updates.
- `schema/list-sdk-docs.input.schema.ts` is generated by the pipeline — do not edit by hand.
- Method-level usage examples are omitted on purpose (`get_map_example` covers them); typedef
  examples are kept to disambiguate data shapes.
- `.github/workflows/update-sdk-docs.yml` opens a PR only when something other than
  `metadata.json` changed (`generatedAt` moves on every run). Check the run log for
  `unmatched typedef`, `event target spec` and `property note` warnings.

**Two deliberate exceptions to "no hardcoded symbol lists"** in `scripts/update-sdk-docs.js`,
both measured by dumping event callback payloads in a live browser page. Each warns when its
target is missing; drop an entry once the upstream docs cover it.

- `EVENT_TARGET_SPECS` adds to `inavi.maps.MarkerClusterer` what upstream still omits: the index
  segment of the target `id` is the position in the `markers` array passed to the constructor —
  the only route from a clicked marker back to its source record.
- `PROPERTY_NOTES` appends a caveat to `EventPayload.target`. Upstream corrected it only on
  `MarkerClusterer#on`, so a reader arriving from another emitter's `relatedTypes` link never
  sees it.
